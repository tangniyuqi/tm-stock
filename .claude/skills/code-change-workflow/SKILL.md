# 代码改动工作流（tm-stock）

> 只读查询、纯解释不必走完整流程；**一旦要改文件，就必须回到这里**。

## 1. 先理解，别急着改

- 这个改动**服务什么业务场景**？不清楚就先问。
- **先检查已有实现**：是不是已经有了？能不能复用？（尤其前端先查 `.kiro/skills/tmui4x-dev/`）
- 🔴 **合规预检**：会碰个股/预测/排序/禁用词吗？

## 2. 定义成功标准（改之前就写下来）

"怎样算改好了" —— 可验证的判据，不是"能跑就行"。

## 3. 检查工作区

`git status` 看有没有未提交的他人改动；明确**改动边界**（改哪些文件、**不动什么**）。

## 4. 可行时测试先行

Go 用表驱动测试；改 bug 时**先写复现用例**再修。

## 5. 实施

遵循 `.claude/agents/` 下对应规范（Go 分层 / uni-app x / 契约对齐）。

## 6. 验证（**这一步不能省**）

```bash
bash scripts/harness-checks.sh        # 合规词 + 密钥 + Go + 前端配置
bash scripts/check-architecture.sh    # 分层约定
```

**语法通过 ≠ 功能正确**：关键逻辑真跑一遍（正例 + 反例）。

## 7. 自审 + 中文交付

- 三问自检：① 最没把握 ② 最大遗漏 ③ 波及面
- 交付说明：做了什么 + 关键路径（file:line）+ 验证结果
- **不写总结文档**

## 完成的判据

见 `.claude/agents/task-completion-rule.md`：需求对齐 + 门禁绿灯 + 真跑验证 + 三问自检，**四条缺一不可**。
