# 前后端 API 契约对齐

> **契约先行**是前后端能并行的唯一前提。契约没定就开工 = 返工。

## 流程

1. 架构阶段在 `docs/specs/{需求}/design.md` 写清契约：**路径 / 方法 / 入参 / 出参 / 错误码**。
2. 前后端**都以该文件为准**；任一方要改，**先改文档再改代码**。
3. 联调前双方各自对照文档自检一遍。

## 统一约定（强制）

| 项 | 约定 |
|---|------|
| 路径 | `/api/v1/<resource>`，小写连字符 |
| 响应包装 | `{ "code": 0, "msg": "", "data": {} }`，code=0 表示成功 |
| **时间字段** | **毫秒时间戳 int64**，禁止返回格式化字符串 |
| 分页 | 入参 `page`/`size`；出参 `{ list: [], total: 0 }` |
| 空值 | 列表返回 `[]` 不返回 null；对象字段缺失显式给零值 |
| 错误码 | 4xxxx 客户端 / 5xxxx 服务端；每个码在 design.md 登记 |

## 时间字段为什么必须是时间戳

前端强类型（uts）下，后端一旦从 number 改成 string，**前端直接崩**（见坑点库 P10）。
统一时间戳可根除这类问题。

## 契约变更纪律

- **破坏性变更**（删字段、改类型、改语义）必须：先同步双方 → 更新 design.md → 约定切换时点。
- 新增字段是安全的；前端要能容忍未知字段。
- 变更后**联调必须重跑**，不能假设"只是加个字段应该没事"。

## 自检

- [ ] design.md 里的契约与实际实现逐字一致？
- [ ] 所有时间字段都是毫秒时间戳？
- [ ] 错误码都登记了？
- [ ] 空列表返回 [] 而非 null？
