# ADR-0011：任务执行预算采用持久化保守预留

状态：开发决策；不开放真实调用、收费或生产部署。

## 背景

任务已有锁定预算和租约，但没有跨重试/接管累积的调用前记账。模型返回的实际用量可能缺失，提交或响应未知时无法证明费用为零；进程内计数或失败后退款会让重启、并发及重试突破上限。TradingAgents-CN 当前适配协议也不能证明受控的逐任务真实用量。

## 选项

1. 返回后按用量扣预算：未知调用无法保守核算。
2. 失败就归还预留：无法区分请求未发出和已计费但回执丢失。
3. 调用前持久化上界，已提交预留不退；相同操作不自动重复执行。

## 决定

采用 3。新增预算计数器与不可变预留明细，服务事务按任务→预算→明细的固定顺序锁定，不反向锁积分。预算限额来自任务的不可变快照；明细绑定任务/用户、操作键、输入摘要、owner/fence 和调用/token/页数上界。数据库在插入明细时原子更新计数器并拒绝超限，服务逐项对账；每任务额外限制至多 1000 条预留，作为保守容量边界，不是定价依据。

相同键/输入/上界返回原预留且 `NewlyReserved=false`，跨接管也不重置；改输入/上界冲突。提交未确认返回空收据，按原键核查不能重新获得新预留。租约失效、取消、任务到期时不新增预留。不存在退款、清零或人工补交后门。确需另一次可证明安全的尝试，必须由未来可信执行策略决定并使用新操作键，仍占原任务预算。

## 后果与边界

- 崩溃发生在预留提交后、发请求前，也会保守损耗预算；宁可任务提前停止，不能把未知成本当零。`NewlyReserved` 不是可转让或长期有效的执行许可。
- 此实现只负责必要的本地预算闸门，不证明外部请求受控。执行层仍须核对有效租约/上下文，强制输入+输出 token 上界、重试次数、页面数量、远端工具与来源策略；不满足时不能调用。不能把保守预留伪装成真实用量或据此追加扣积分。
- 保留既定锁价与账本政策，不冻结/释放/结算积分，不修改会员接口、L0 或上游代码。本轮不实现 worker、实际用量审计、阶段结果复用或成功报告结算。
- 旧任务迁移不自动初始化或伪造历史消耗；新预算表缺失时任务联合自检必须拒绝通过，后续启动入口须接线。生产升级、权限与真实成本另行验证。
